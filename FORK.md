# Форк QMedia

Это форк [googleads/google-ads-mcp](https://github.com/googleads/google-ads-mcp): добавлены сбор семантики и Реестр Аккаунтов. Используется агентом из репозитория [qmedia-ads-agent](https://github.com/qmedia-by/qmedia-ads-agent).

## Зачем форк

Официальный сервер отдаёт три инструмента: `search` (GAQL), `get_resource_metadata`, `list_accessible_customers`. Собрать через них семантику невозможно: `KeywordPlanIdeaService.GenerateKeywordIdeas` — отдельный RPC, а не запрашиваемый через GAQL ресурс. При этом сбор семантики — центральный сценарий нашего агента.

Сторонние MCP-серверы (gomarble и аналоги) умеют keyword planner из коробки, но возвращают зависимость от вендора, от которой проект уходит.

Вторая причина появилась позже. Upstream не знает, что такое Клиент: он оперирует `customer_id`, и `list_accessible_customers` возвращает голые числа, в которых Менеджер, ведущий два десятка Клиентов, не опознаёт нужного. Связка «Клиент → Аккаунты» жила файлом в репозитории агента, но тот репозиторий публичный, и список клиентов агентства с их идентификаторами в нём быть не должен. Реестр переехал в закрытую таблицу агентства, читать которую умеет только сервер — см. «Реестр Аккаунтов».

## База

Патч наложен поверх коммита upstream **`91beff7`** (`main`, версия Google Ads API **v24**).

Тегов upstream не публикует, поэтому база фиксируется коммитом, а не тегом — это отличие от исходной формулировки решения в `qmedia-ads-agent/docs/adr/0005`.

## Обновление с upstream

```bash
git fetch upstream
git log --oneline 91beff7..upstream/main    # что изменилось с нашей базы
```

Порядок: смержить новую базу, переналожить патч, обновить SHA в этом файле, **перегенерировать golden-файлы smoke-тестов** — `nox -s smoke_tests` падает, пока `tests/smoke/golden_tools_list.json` не содержит наш инструмент:

```bash
pip install google-genai && python -m tests.smoke.generate_golden
```

Зависимость `google-genai` генератору нужна для импорта, хотя сам golden от неё не зависит; без неё он падает на `ModuleNotFoundError`.

## Локальная разработка

Требуется Python 3.10+ (upstream тестируется на 3.10–3.13).

```bash
python3.13 -m venv .venv && .venv/bin/pip install -e . black
.venv/bin/python -m unittest discover --buffer -s=tests -p "*_test.py"
.venv/bin/python -m unittest tests/smoke/smoke_test.py
.venv/bin/black -l 80 .
```

Ширина строки — 80, как в `noxfile.py`; дефолтные 88 у black дадут расхождение с upstream.

Следить нужно за двумя независимыми осями. Первая — релизы upstream. Вторая — **версия Google Ads API**: мажорная версия живёт около года, после чего запросы к ней блокируются с `UNSUPPORTED_VERSION`. Сейчас в коде v24 (`ads_mcp/utils.py`, `ads_mcp/tools/core.py`, `ads_mcp/tools/keyword_planning.py`, `ads_mcp/resources/discovery.py`). Заведите напоминание за два месяца до sunset — иначе первым признаком проблемы станет отказ у всех менеджеров разом.

## Требования к доступу

Инструмент работает только если developer token имеет permissible use **«Researching keywords and recommendations»**. На уровне доступа Explorer `KeywordPlanService`, `KeywordPlanIdeaService` и `KeywordPlanCampaignService` заблокированы, и код это не обходит.

Для нашего токена (уровень Standard) доступ проверен прямым вызовом REST API и подтверждён.

## Развёртывание

Docker на хостинге агентства, рядом Redis. Google Cloud Run не используется: платёж Google из региона не проходит, поэтому billing account недоступен. Приложению это безразлично.

Сервис живёт на `https://google-ads-mcp.qmedia.by` и выкатывается из GitHub Actions при пуше в `dev`.

### Стек

`docker/docker-compose-server.yml` — два сервиса:

- **mcp** — образ `ghcr.io/qmedia-by/google-ads-mcp:<sha>`, собирается CI. Внутри слушает `8080`, наружу публикуется только на `127.0.0.1:${PORT_MCP}`; домен и TLS даёт reverse-proxy панели ispmanager.
- **redis** — сток `redis:7.2-alpine` с AOF и паролем, на хост не публикуется. Хранит регистрации OAuth-клиентов и токены Менеджеров. Политику вытеснения не задаём намеренно: `maxmemory-policy` начал бы молча выбрасывать токены под нагрузкой — ровно то, ради предотвращения чего Redis здесь и стоит.

Кода на сервере нет, всё внутри образа. Поэтому здесь нет ни выкладки приложения rsync'ом, ни бэкапа, ни отката кода, которые есть в соседнем `influenso`: единственное, что имеет смысл откатывать, — тег образа.

### Хранилище и ключ подписи

Регистрации OAuth-клиентов и токены Менеджеров живут в `client_storage`. Дефолтный бэкенд не переживает перезапуск контейнера, `GOOGLE_ADS_MCP_STORAGE_TYPE=redis` переживает — этим Redis и оправдан.

`GOOGLE_ADS_MCP_JWT_SIGNING_KEY` строго обязательным при этом **не** является, вопреки тому, что можно предположить: не задав его, FastMCP выводит ключ подписи детерминированно из `GOOGLE_ADS_MCP_OAUTH_CLIENT_SECRET` — HKDF с фиксированной солью, `fastmcp/server/auth/jwt_issuer.py`. После перезапуска ключ будет тем же, и токены останутся валидными.

Мы всё равно задаём его явно, и не ради перезапусков: с ним срок жизни токенов не привязан к client secret, и ротация секрета в GCP не разлогинивает весь отдел заодно. Цена — обратная связь: ротация самого ключа разлогинивает всех и обнуляет хранилище, потому что `ads_mcp/auth_storage.py` выводит из него же ключ шифрования. Отдельный `GOOGLE_ADS_MCP_STORAGE_ENCRYPTION_KEY` поэтому не заводим — одним секретом меньше.

### Регистрация клиентов: CIMD выключен

`GoogleProvider` по умолчанию включает **CIMD** (Client ID Metadata Document) — `enable_cimd: bool = True`. Когда он включён, сервер безусловно ставит `client_id_metadata_document_supported: true` в `/.well-known/oauth-authorization-server` (`fastmcp/server/auth/oauth_proxy/proxy.py:2107`), не проверяя, способен ли он этот документ забрать.

Дальше цепочка ломается: Claude Code видит флаг, **пропускает** динамическую регистрацию и подставляет URL-client_id `https://claude.ai/oauth/claude-code-client-metadata`. Сервер должен сам сходить по этому URL — из контейнера это не работает, и `/authorize` отбивает клиента страницей «client ID was not found in the server's client registry». Совет с той страницы («сбросьте токены и переподключитесь») зацикливает: после переподключения клиент прочитает тот же флаг и подставит тот же URL. Настоящая причина уходит в `logger.warning` (`fastmcp/server/auth/cimd.py:745`, строка `CIMD fetch failed`).

Поэтому в `ads_mcp/coordinator.py` передаём `enable_cimd=False`. Флаг уходит из метаданных, клиенты возвращаются к регистрации через `/register`, а она у нас рабочая и переживает перезапуск — регистрации лежат в Redis. Вариант с открытием egress до `claude.ai` отвергнут: он привязывает вход Менеджеров к доступности стороннего домена за Cloudflare. Вернуть CIMD имеет смысл, только если появится клиент, не умеющий динамическую регистрацию, — и тогда egress придётся проверять отдельно.

Проверено на `fastmcp 3.4.7`; в `pyproject.toml` стоит `fastmcp>=3.2.0`, так что при обновлении FastMCP стоит убедиться, что аргумент не переименован.

### Переменные окружения

Файл `.env` лежит **на уровень выше** `docker/`, в корне `DEPLOYMENT_FOLDER`: CI перезаписывает `docker/` при каждом деплое и снёс бы файл, положенный внутрь. Шаблон — `docker/.env.server.example`. Читает файл только compose (`--env-file`); CI трогает в нём единственную строку `IMAGE_TAG`.

| Переменная | Назначение |
|---|---|
| `PORT_MCP` | хостовый порт для reverse-proxy, `16800`. Должен быть уникален на сервере |
| `IMAGE_TAG` | тег образа; переписывается CI при каждом деплое |
| `REDIS_PASSWORD` | пароль Redis, `openssl rand -hex 16` |
| `GOOGLE_ADS_DEVELOPER_TOKEN` | developer token агентства |
| `GOOGLE_ADS_LOGIN_CUSTOMER_ID` | MCC, через который идёт доступ к Аккаунтам |
| `GOOGLE_ADS_REGISTRY_SHEET_ID` | id таблицы Реестра — часть URL между `/d/` и `/edit`. Обязательна и непуста |
| `GOOGLE_ADS_REGISTRY_SA_KEY` | JSON-ключ service account целиком в base64. Обязательна и непуста |
| `GOOGLE_ADS_REGISTRY_RANGE` | необязательна: диапазон чтения, по умолчанию `A1:Z2000` первой вкладки |
| `GOOGLE_ADS_MCP_OAUTH_CLIENT_ID` | OAuth client (тип Web application) |
| `GOOGLE_ADS_MCP_OAUTH_CLIENT_SECRET` | там же |
| `GOOGLE_ADS_MCP_BASE_URL` | `https://google-ads-mcp.qmedia.by`; Authorized redirect URI = этот адрес плюс `/auth/callback` |
| `GOOGLE_ADS_MCP_JWT_SIGNING_KEY` | ключ подписи токенов, `openssl rand -hex 32`. Технически необязателен, но задаём — см. выше |

Секреты живут только в этом файле на сервере и в репозиторий не попадают.

Чего в файле нет и почему:

- `GOOGLE_ADS_MCP_STORAGE_TYPE`, `GOOGLE_ADS_MCP_STORAGE_REDIS_URL`, имя compose-проекта, репозиторий образа — свойства стека, а не окружения; прибиты в `docker-compose-server.yml`.
- `FASTMCP_HOST` — ни на что не влияет: `ads_mcp/server.py` передаёт `host="0.0.0.0"` явным аргументом.
- `GOOGLE_PROJECT_ID` — остаток инструкции про Cloud Run, кодом не читается.

### Контроль доступа: три списка

Списков, определяющих доступ Менеджера, **три**, и они независимы:

| Список | Где живёт | Что даёт |
|---|---|---|
| **Test users** | GCP, OAuth consent screen | право **войти** — пройти OAuth и получить токен |
| **Пользователи MCC** | Google Ads, Admin → Access and security | право **дотянуться до Аккаунтов** через MCC |
| **Реестр Аккаунтов** | таблица агентства в Google Sheets | **какие именно Аккаунты** разрешено запрашивать |

Первые два — про Менеджера, третий — про Аккаунты, и заводятся они в трёх разных местах. Попадание в первый список не даёт ничего во втором. Поэтому подключение Менеджера — это **две** операции в двух разных консолях; на чтение доступа в MCC достаточно.

Менеджер, заведённый только в Test users, успешно логинится, получает рабочий токен, инструменты подключаются — и любое обращение к Аккаунту отбивается:

```
User doesn't have permission to access customer. Note: If you're accessing a
client customer, the manager's customer id must be set in the 'login-customer-id'
header.
```

Подсказка из текста ошибки уводит в сторону: `login-customer-id` сервер выставляет из `GOOGLE_ADS_LOGIN_CUSTOMER_ID`, и дело не в нём. API проверяет, что **аутентифицированный пользователь** заведён в указанном MCC; если нет — запрос отклоняется при любом значении заголовка. Признак этого — пустой `customers_list_accessible_customers`, см. «Эксплуатация».

Из первого списка следует и срок жизни сессий: OAuth-приложение остаётся в статусе Testing, поэтому Google аннулирует refresh-токены каждые 7 дней, а войти могут только аккаунты из Test users. Он же работает как allowlist Менеджеров.

#### Третий список: какие Аккаунты

Первых двух списков мало. Менеджер, заведённый в MCC, дотягивается до **любого** Аккаунта агентства, а не только до Аккаунтов своих Клиентов, — достаточно опечатки в `customer_id`, чтобы агент вытащил цифры чужого Клиента. Это добавление форка: в upstream такого слоя нет. См. `qmedia-ads-agent/docs/adr/0003`.

Разрешённые Аккаунты — это **Аккаунты из Реестра**, и ничего сверх них. Отдельной переменной `GOOGLE_ADS_ALLOWED_CUSTOMER_IDS` больше нет: она была копией Реестра, снятой вручную, поэтому подключение Клиента состояло из двух операций в двух местах, и эти два места расходились. Симптом расхождения — отказ по Аккаунту, который в Реестре уже есть. Один источник убирает не случай, а весь класс.

Логика — в `ads_mcp/access_control.py`, отдельным модулем, чтобы правки upstream-файлов остались однострочными. Три точки применения:

| Инструмент | Поведение |
|---|---|
| `search_search` | отказ: `ToolError` с номером запрошенного Аккаунта и списком разрешённых |
| `planning_generate_keyword_ideas` | то же |
| `customers_list_accessible_customers` | **фильтрация выдачи**, а не отказ |

`metadata_get_resource_metadata` не трогаем: он описывает схему API, а не данные Аккаунта, и `customer_id` не принимает. Инструменты `registry_*` тоже: они отдают связку «Клиент → Аккаунты», а не данные из Google Ads, и ограничивать их нечем — Реестр и есть граница.

Выдача фильтруется, а не отклоняется, потому что это инструмент обнаружения: Аккаунт, который агенту всё равно запретят запросить, незачем предлагать ему как вариант. Обратная сторона — при пустом пересечении Менеджер увидит «нет доступных Аккаунтов» вместо внятной ошибки, неотличимо от незаведённости в MCC выше; в логах сервера при этом будет строка `The Registry hid N of M accessible accounts`.

Проверка идёт **до** обращения к Google: отказ не тратит квоту и не требует валидных учётных данных. Стоит она при этом словарного поиска, а не сетевого запроса, — снимок Реестра лежит в памяти процесса, см. ниже.

Правила:

- **Реестр не сконфигурирован — ограничений нет.** Это поведение upstream, и оно же позволяет гонять тот же образ локально без service account. Именно поэтому preflight деплоя требует от обеих переменных Реестра **непустого** значения: выключить контроль доступа опечаткой быть нельзя.
- **Реестр сконфигурирован, но нечитаем — запрещено всё.** Не «ограничений нет»: неизвестный allowlist — не пустой. Отказ прямо говорит, что чинить надо сервер, а не запрос. Случай редкий: пустым снимок бывает только на первом старте процесса, у которого ещё и Redis пуст.
- Дефисы и пробелы игнорируются: `123-456-7890` и `1234567890` — один и тот же Аккаунт, с обеих сторон сравнения. Менеджер копирует номер из интерфейса Google Ads в дефисах, и отказывать ему из-за пунктуации незачем.
- Если в Реестре **ни одного** Аккаунта Google Ads, запрещены все. Тот же fail-closed, и текст ошибки отсылает к администратору.

### Реестр Аккаунтов

Связку «Клиент → его Аккаунты у Провайдеров» держит таблица агентства в Google Sheets. Она закрыта, и читает её **service account**, а не общий человеческий логин: доступ выдан одному этому серверу и отзывается удалением одного viewer'а из шаринга файла. Сервер только читает; таблицу правят люди.

Модулей три, и делятся они по тому, что каждый знает:

| Модуль | Отвечает за |
|---|---|
| `ads_mcp/registry.py` | сходить в Sheets API, разобрать строки, проверить их |
| `ads_mcp/registry_cache.py` | снимок в памяти, копия в Redis, обращение к сети не чаще, чем раз в 5 минут |
| `ads_mcp/tools/registry.py` | инструменты `registry_find_client` и `registry_list_clients` |

Новых зависимостей нет ни одной: `google-auth` (подпись JWT service account) приходит с `google-ads`, `httpx` — с fastmcp, `redis` — с `py-key-value-aio[redis]`, который форк и так объявляет.

#### Почему кэш синхронный

Инструменты upstream — обычные `def`, не `async def`. Асинхронное чтение Реестра заставило бы переписать их сигнатуры, и дельта форка к чужим файлам выросла бы с трёх строк до переписанных функций — при следующем мерже upstream это конфликт на ровном месте. Поэтому снимок лежит в памяти процесса, `access_control` читает словарь, а за сеть отвечает тот же синхронный код под одним `threading.Lock`. Десять одновременных вызовов дают одно чтение таблицы, а не десять.

TTL — 5 минут, и он не про отслеживание правок: связка меняется при подписании Клиента, то есть раз в месяц. Он про то, чтобы каждый вызов инструмента не ждал Google. Клиента, добавленного минуту назад, это не прячет: `registry_find_client`, не найдя имени, принудительно перечитывает таблицу, и «такого Клиента нет» звучит только после свежего чтения.

#### Когда таблица недоступна

Снимок переживает перезапуск: копия лежит в том же Redis, что и токены Менеджеров, — с AOF и без политики вытеснения, так что оттуда ничего не пропадает молча. Срока жизни у копии нет намеренно. Протухающая сама по себе копия оставила бы перезапускающийся сервер ни с чем ровно в тот момент, когда он меньше всего может себе это позволить; она просто перезаписывается при каждом удачном чтении.

Пока снимок есть, сервер работает по нему и **говорит об этом**: инструменты `registry_*` возвращают поле `warning` с возрастом копии, агент передаёт его Менеджеру. Лог на сервере никто не читает, а сходить к владельцу таблицы может как раз Менеджер.

Владелец таблицы — вне контроля этого репозитория, и это принятый риск, а не недосмотр: если файл удалят или отзовут доступ, восстанавливать Реестр придётся из снимка в Redis вручную.

#### Схема таблицы

Таблица — рабочий документ агентства, а не выгрузка, и устроена она соответственно.

**Это не одна таблица, а несколько блоков подряд на одной вкладке**, у каждого своя строка заголовков и свой набор колонок: блок отдела PPC (там Google Ads), блок таргетинга (там Meta, TikTok, VK), блок с доступами. Один Клиент штатно встречается в нескольких блоках — Google Ads в одном, VK в другом. Поэтому блоки читаются по очереди, а Клиенты **склеиваются по имени проекта**.

Имя Клиента — это домен, и один и тот же домен написан по-разному: `kofta.by`, `https://kofta.by/`, `www.pamiar.by`. Схема, протокол и завершающий слэш срезаются перед склейкой — иначе один Клиент стал бы тремя.

**Читаются ровно две колонки: «Google Ads» и «VK реклама».** Это не осторожность, а необходимость: в колонке «Яндекс Директ» у части проектов в одной ячейке лежит логин кабинета вместе с паролем, а отдельный блок «Аккаунт / Доступы» — это пароли от соцсетей. Затянуть их в снимок, в Redis и в контекст агента нельзя, а надёжнее всего это гарантируется тем, что такие колонки просто не разбираются. Технически это делает список синонимов в `_PROVIDER_ALIASES` (`ads_mcp/registry.py`): колонка, не названная там, не читается, а **блок, где не нашлось ни одной колонки Провайдера, пропускается целиком**. Яндекс Директ отсутствует в Реестре осознанно — контекст его кабинетов у агента и так есть, через LidFly.

Из-за этого часть проектов таблицы в Реестр не попадает: у них нет ни Google Ads, ни VK — только Директ, Meta или TikTok. На данных на момент написания это около 28 строк из 92. Агент по ним ответит «такого Клиента в Реестре нет», и это правда: Аккаунта, к которому он мог бы обратиться, у Клиента действительно нет.

**Ячейка не равна идентификатору.** В колонке Google Ads встречается почта рядом с номером, пометки вроде «РБ/РФ» и «Казахстан» с двумя кабинетами в одной ячейке, прочерки `-` и `–` вместо пустоты. Поэтому из ячейки **выбираются все** подстроки формы `123-456-7890` или десяти цифр подряд, а прозаические подписи не разбираются: определять по ним, какой кабинет чей, значит возвращаться к угадыванию, от которого Реестр и защищает. Несколько кабинетов у одного Клиента — штатная ситуация (на текущих данных таких трое), и `registry_find_client` в этом случае требует у Менеджера уточнить, какой имеется в виду, а не складывает их числа. Лукахеды в регулярке не дают выкусить десять цифр из более длинного числа — телефона или id счётчика.

VK-ячейка написана как «человеческое имя (12345678)» или «имя (ID 12345678)», и берётся **только число в скобках**. Всё остальное в ячейке — логины, телефоны — остаётся в ячейке.

Колонка «активен/архив» в таблице отсутствует, и угадывать её по другим полям мы не будем: тихо выброшенный из allowlist живой Клиент хуже, чем оставшийся в нём архивный.

#### Что проверяется при чтении

PR-ревью у таблицы нет, поэтому проверки переехали в момент чтения:

- заполненная ячейка, из которой не удалось вытащить ни одного идентификатора, отмечается проблемой с номером строки и именем проекта — Клиент при этом сохраняет остальные свои Аккаунты;
- строка с идентификаторами, но без имени проекта, пропускается с проблемой;
- один Аккаунт у двух Клиентов **не** достаётся молча первому: это отдельная проблема, потому что тихий выбор здесь означает отчёт по чужому Клиенту. В allowlist такой Аккаунт при этом остаётся — спорна принадлежность, а не сам Аккаунт;
- Клиент, у которого не осталось ни одного читаемого Аккаунта, в Реестр не попадает.

Пустые строки-разделители и прочерки вместо значений — норма для таблицы, которую ведут руками, и о них не сообщается.

Отдельно от этого: таблица, которую **не удалось разобрать вообще** — не найдено ни одного заголовка, ни под одним из них нет Клиента с читаемым Аккаунтом, — считается недоступной, а не пустой. Пустой Реестр означал бы пустой allowlist, то есть блокировку всего агентства из-за переименованной колонки.


### Первый запуск

Порядок жёсткий: ошибка на любом шаге даёт невнятный отказ на первом деплое.

1. **Поддомен и TLS.** Завести `google-ads-mcp.qmedia.by`, выпустить сертификат. Проверка: `curl -I https://google-ads-mcp.qmedia.by` отвечает чем угодно, кроме ошибки TLS.
2. **OAuth-клиент.** В GCP у клиента типа Web application добавить Authorized redirect URI `https://google-ads-mcp.qmedia.by/auth/callback`. Проверка: URI виден в списке после сохранения.
3. **Каталог проекта.** Создать `DEPLOYMENT_FOLDER` на сервере, внутри — пустой `docker/`.
4. **Секреты.** `openssl rand -hex 16` для `REDIS_PASSWORD`, `openssl rand -hex 32` для `GOOGLE_ADS_MCP_JWT_SIGNING_KEY`.
5. **Доступ к Реестру.** Шаг проходится скриптом — см. «Настройка доступа к Реестру» ниже. Вручную это: в том же GCP-проекте включить **Google Sheets API**, создать service account без ролей в проекте, скачать JSON-ключ, и попросить владельца таблицы выдать этому роботу доступ **Viewer адресно** — не «доступ по ссылке». Проверка: адрес робота виден в списке доступа к файлу.
6. **`.env`.** Скопировать `docker/.env.server.example` в `DEPLOYMENT_FOLDER/.env` и заполнить; переменные Реестра допишет тот же скрипт, ключ — `base64 -w0 key.json`. Проверка: `grep CHANGE_ME .env` ничего не находит.
7. **Reverse-proxy.** Вписать блок из следующего раздела в конфиг сайта в ispmanager.
8. **Секреты GitHub.** В Environment `production`: `DEPLOYMENT_HOST`, `DEPLOYMENT_USER`, `DEPLOYMENT_FOLDER`, `DEPLOYMENT_SSH_PRIVATE_KEY`.
9. **Менеджер.** Его Google-аккаунт — в Test users (GCP) **и** пользователем в MCC (Google Ads). Две операции, см. «Контроль доступа». Проверка: после входа `customers_list_accessible_customers` возвращает непустой список, и в нём виден id MCC.

Дальше — пуш в `dev`: соберётся образ, поднимется стек, пройдёт health check.

#### Настройка доступа к Реестру

Шаги 5 и 6 разложены по консолям — GCP, шаринг чужого файла, `.env` по SSH — и ошибка в любом из них вскрывается только отказом у Менеджеров после деплоя. Поэтому они собраны в скрипт:

```bash
./scripts/setup-registry-access.sh
```

Он включает Sheets API, доводит до созданного service account, показывает его адрес для шаринга и дописывает переменные в `.env` на сервере — с копией старого файла и подтверждением перед правкой. Ключ на экран не выводится и уходит на сервер пайпом в `ssh`.

Ключевая его часть — предпоследний шаг: скрипт читает таблицу **тем же `ads_mcp.registry.fetch()`**, что потом будет работать на сервере, и печатает, сколько Клиентов разобралось и сколько `customer_id` попало в allowlist. Невыданный шаринг, невключённый API и переименованная колонка обнаруживаются здесь, до того как что-то поедет в прод. Для этого шага нужен собранный `.venv` — см. «Локальная разработка».

Id таблицы и адрес её владельца скрипт спрашивает и нигде не хранит: репозиторий публичный, и этим данным в нём не место — см. `qmedia-ads-agent/docs/adr/0008`.

#### Переход на Реестр на уже работающем сервере

`.env` на сервере правится руками, поэтому первый деплой после появления Реестра упадёт на preflight: старая переменная там есть, новых нет. Тот же скрипт снимает и это — он удаляет `GOOGLE_ADS_ALLOWED_CUSTOMER_IDS` и дописывает новые переменные. Сделать это надо **до** пуша в `dev`, иначе деплой остановится на первом же шаге.

Порядок именно такой: сначала сервер учится читать Реестр и проверяется на реальном Клиенте, и только потом Реестр уходит из `qmedia-ads-agent`. Обратный порядок оставляет агента без Реестра совсем.

### Reverse-proxy в ispmanager

MCP по streamable HTTP держит длинные SSE-ответы, и дефолтный конфиг их ломает: буферизация склеивает поток, а `proxy_read_timeout 60s` рвёт его на середине долгого `planning_generate_keyword_ideas`.

```nginx
location / {
    proxy_pass http://127.0.0.1:16800;
    proxy_http_version 1.1;
    proxy_set_header Host $host;
    proxy_set_header Connection "";
    proxy_buffering off;
    proxy_read_timeout 3600s;
}
```

Заголовки `X-Forwarded-*` не нужны: абсолютные URL FastMCP строит из `GOOGLE_ADS_MCP_BASE_URL`, а не из заголовков прокси.

### Деплой и откат

`.github/workflows/deployment.yml`, три блока: `quality` (вызывает `ci.yml`; красный — деплой не идёт) → `image` (сборка и push в GHCR под тегами `<sha>` и `latest`) → `release` (preflight `.env` → rsync `docker/` → `pull` → `up -d --wait` → health check).

Health check — `GET /.well-known/oauth-authorization-server`. Это единственный роут FastMCP, отдающий 200 без авторизации, и появляется он только когда OAuth-провайдер поднялся: 200 доказывает больше, чем открытый TCP-порт. В образе `python:3.11-slim` нет ни `curl`, ни `wget`, поэтому healthcheck контейнера написан на `urllib`.

Автооткат: `release` запоминает текущий `IMAGE_TAG` до переключения и возвращает его, если `up --wait` или health check упали.

Ручной откат на произвольный тег — `workflow_dispatch` с полем `image_tag`. Блоки `quality` и `image` при этом пропускаются: аварийный откат не должен блокироваться красными тестами текущей ветки. То же самое руками:

```bash
cd $DEPLOYMENT_FOLDER
sed -i 's|^IMAGE_TAG=.*|IMAGE_TAG=<sha>|' .env
docker compose --env-file .env -f docker/docker-compose-server.yml up -d
```

### Эксплуатация

```bash
cd $DEPLOYMENT_FOLDER
docker compose --env-file .env -f docker/docker-compose-server.yml ps
docker compose --env-file .env -f docker/docker-compose-server.yml logs -f mcp
```

Логи ротируются драйвером json-file (10 МБ × 3 на сервис): сервер общий, без лимита они пухнут бесконечно. Успешный деплой делает `docker image prune -f` — он трогает только dangling-образы и не может удалить тег, на который откатываются.

**Чего не ловят ни preflight, ни health check.** `GOOGLE_ADS_DEVELOPER_TOKEN` читается лениво, в момент вызова инструмента (`ads_mcp/utils.py`). Контейнер с неверным токеном поднимется, пройдёт health check и будет выглядеть здоровым — сломается только у Менеджера. Preflight ловит лишь отсутствие переменной и незаполненный плейсхолдер.

**Реестр не читается.** Признак со стороны Менеджера — либо пометка «данные Реестра от …» в ответе агента, либо отказ «сервер не может определить, какие Аккаунты ему разрешены». Со стороны сервера — `WARNING`/`ERROR` от `ads_mcp.registry_cache` с причиной: 401/403 означают, что таблицу перестали шарить на service account или в проекте выключили Sheets API; 404 — что файл удалили, переименовали вкладку или сменили `GOOGLE_ADS_REGISTRY_RANGE`; «No header row» — что в таблице переименовали колонки.

Пока в Redis есть снимок, агентство работает по нему, и это не авария, а повод сходить к владельцу таблицы. Аварией это становится при перезапуске контейнера с пустым Redis: тогда запрещены все Аккаунты, и до восстановления доступа к таблице сервер не отдаст ничего.

**Отказ «User doesn't have permission to access customer».** Первым делом — `customers_list_accessible_customers`. Это самая дешёвая и однозначная проверка: пустой список означает, что Google-аккаунт, которым прошли OAuth, не заведён пользователем ни в одном Аккаунте Google Ads, включая MCC агентства. Он же отделяет «Менеджер не заведён в Google Ads» от «Аккаунт не под нашим MCC» и от «протух токен» — снаружи все три выглядят одинаково, отказом на любом инструменте (падают и `planning_generate_keyword_ideas`, и `search_search` по ресурсу `customer`, то есть дело не в keyword planning и не в правах developer token).

Лечится это заведением Менеджера пользователем в MCC (Google Ads → Admin → Access and security) либо переавторизацией тем аккаунтом, который в MCC уже заведён — частый случай, когда OAuth случайно прошли личным аккаунтом вместо рабочего. Пока список пуст, любое обращение к Аккаунту будет отклонено.

Ротация `GOOGLE_ADS_MCP_JWT_SIGNING_KEY` — вторая причина внезапного перелогина: она обесценивает все выданные сессии разом. Планируйте её на тихое время.

**Отказ «The request took too long to respond.»** Это перегрузка на стороне Google, а не наш таймаут, и **менять `proxy_read_timeout` бесполезно**: дедлайн наступает у Google, до нашего прокси дело не доходит. Отличить можно по форме сообщения — префикс `Request ID:` означает структурированный ответ API, тогда как таймаут reverse-proxy дал бы 504 без тела, а клиентский gRPC-дедлайн — `DeadlineExceeded` вообще без `request_id`.

Сам инструмент такие отказы уже переживает: `ads_mcp/tools/keyword_planning.py` различает `InternalError.DEADLINE_EXCEEDED` и `TRANSIENT_ERROR` (в описании второго Google прямо просит повторить запрос) и повторяет вызов дважды, с паузами 2 и 4 секунды. Ниже не повторяет никто: сгенерированный транспорт оборачивает этот RPC без `default_retry`, а параметр `retry` в сигнатуре метода видит только транспортные коды и до семантики `GoogleAdsFailure` не добирается. Отказ с другим кодом ошибки — и failure, где к транзиентной ошибке примешана постоянная, — уходит Менеджеру сразу, без повторов.

Если отказ всё-таки дошёл до Менеджера, значит не помогли и повторы. Практически всегда это несколько тяжёлых вызовов, запущенных параллельно: они кладут и себя, и следующий за ними одиночный запрос. Лечится последовательными вызовами и меньшим числом сидов. Ограничения на число сидов у API нет — отказ вызывает суммарный вес одновременных запросов, поэтому один и тот же запрос через минуту проходит без ошибок. Параметр `limit` в этом не помощник и защитой от дедлайна не является: он обрезает уже полученный ответ на нашей стороне, а сам запрос уходит без ограничения размера.
